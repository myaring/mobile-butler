# 기여 양식 및 규칙

기여 및 참여에 필요한 최소한의 양식 및 규칙입니다.

이 프로젝트는 현업 개발자부터 Android가 처음인 분까지 함께 참여하는 오픈 협업 프로젝트입니다.
그래서 이 문서의 규칙은 **지키지 않으면 안 되는 금지 사항이 아니라, 서로 같은 작업을 두 번 하지 않기 위한 권장 양식**입니다.
익숙하지 않은 부분이 있으면 그대로 올려주시고 Discord에 물어보시면 됩니다. 양식 때문에 PR을 못 올리는 상황이 더 아깝습니다.

PR을 올리는 절차와 양식은 [PR 룰](PR_rules.md)에 따로 정리되어 있습니다.

---

## 역할

| 역할 | 할 수 있는 일 |
| --- | --- |
| 프로젝트 오너 | PR 승인(accept)과 머지(merge), 브랜치 전략 결정, 마일스톤 관리 |
| 참여자 | 이슈 등록, 브랜치 생성, PR 생성, 다른 사람 PR에 의견 남기기 |

**PR은 참여자 누구나 보낼 수 있지만, accept와 merge는 프로젝트 오너만 합니다.**
참여자끼리 서로 코드를 봐주고 의견을 남기는 것은 환영합니다. 다만 그 의견이 승인을 대체하지는 않습니다.

## 브랜치 전략

브랜치는 `master`와 `dev` 두 개를 축으로 운용합니다.

| 브랜치 | 역할 | 직접 커밋 |
| --- | --- | --- |
| `master` | 실제 서비스로 나갈 코드만 모읍니다. `dev`에서 검증된 항목을 오너가 머지합니다 | ✗ |
| `dev` | 모든 개발 사항을 통합하는 기준 브랜치입니다 | ✗ |
| 작업 브랜치 | 개인이 기능·문서 단위로 만들어 쓰는 브랜치 | ○ |

**모든 작업은 `dev`에서 브랜치를 따서 시작하고, PR도 `dev`로 보냅니다.**
`master`로 바로 PR을 보내지 않도록 주의해주세요. `master`로 가는 머지는 오너가 릴리스 시점에 따로 진행합니다.

```
master  ──────────────●───────────────────●──   (릴리스 시점에 오너가 머지)
                      ↑                   ↑
dev     ──●──●──●──●──┴──●──●──●──●──●──●─┴──   (개발 통합 기준)
          ↑  ↑     ↑        ↑     ↑
       각자 작업 브랜치에서 PR
```

### 브랜치 이름

`<종류>/<짧은-설명>` 형태를 씁니다. 설명은 영문 소문자와 하이픈을 권장합니다.

```
feat/goal-input-screen
fix/notification-delay
docs/kickoff-schedule
chore/room-dependency
```

종류는 아래 커밋 메시지의 종류와 같은 것을 쓰시면 됩니다.

### 작업 시작 전 `dev` 최신화

여러 명이 동시에 작업하기 때문에, 브랜치를 새로 만들 때는 최신 `dev`에서 시작하는 것이 충돌을 가장 많이 줄여줍니다.

```bash
git switch dev
git pull
git switch -c feat/goal-input-screen
```

작업이 길어져서 그동안 `dev`가 많이 바뀐 경우에는, PR을 올리기 전에 한 번 최신 `dev`를 받아와 충돌을 미리 해결해주시면 리뷰가 훨씬 수월합니다.

```bash
git switch dev && git pull
git switch feat/goal-input-screen
git merge dev
```

> 충돌 해결이 어려우면 혼자 오래 붙잡지 말고 Discord에 상황을 올려주세요. 되돌리는 게 더 비싼 작업입니다.

## 커밋 메시지

`<종류>: <한 줄 요약>` 형태를 권장합니다. 요약은 한국어로 써도 괜찮습니다.

```
feat: 목표 입력 화면 추가
fix: 자정 재계산이 하루 밀리는 문제 수정
docs: 기능 정의 초안에 페이싱 엔진 설명 보강
chore: Room 종속성 추가
```

| 종류 | 쓰는 경우 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 작성·수정 |
| `refactor` | 동작은 그대로 두고 구조만 정리 |
| `test` | 테스트 코드 |
| `chore` | 빌드 설정, 종속성, 그 외 잡일 |

커밋을 몇 개로 쪼갤지는 자유입니다. 다만 **"작업 중"**, **"수정"**, **"ㅇㅇ"** 같이 나중에 아무도 알아볼 수 없는 메시지만 피해주시면 됩니다.

## 작업 전 확인할 것

### 1. 이슈를 먼저 보기

같은 걸 두 사람이 만들고 있는 상황이 제일 아깝습니다.
작업을 시작하기 전에 GitHub 이슈를 한 번 보고, **내가 이걸 하겠다는 것을 이슈에 댓글로 남기거나 Discord에 적어주세요.** 이슈가 없으면 새로 만들어주시면 됩니다.

### 2. 커밋에 들어가면 안 되는 파일

로컬 환경 파일이 커밋에 섞여 들어가면 다른 사람 빌드가 깨집니다. `.gitignore`에 대부분 등록되어 있지만, 커밋 전에 `git status`로 한 번 확인해주세요.

- `local.properties` — SDK 경로 등 개인 환경 설정
- `.idea/`, `.gradle/`, `build/` — IDE·빌드 산출물
- API 키, 토큰, 비밀번호가 담긴 파일

> 이 프로젝트는 서버 없는 로컬 전용이라 API 키가 들어갈 일이 거의 없습니다. 만약 필요해지면 코드에 직접 넣지 말고 먼저 Discord에서 의논해주세요.

## 소통

| 용도 | 장소 |
| --- | --- |
| 논의, 질문, 막힌 부분 | Discord |
| 결정된 내용, 할 일 추적 | GitHub 이슈 |
| 작업 기록 | [개발 일지](dev-log/README.md) |

Discord에서 이야기가 정리되면 **결론은 GitHub 이슈에 남겨주세요.** 채팅은 흘러가지만 이슈는 남습니다.

작업한 내용은 [개발 일지](dev-log/README.md)에 남겨주세요. 한 줄로 끝나는 작업은 타임라인 표에 한 줄만 추가하고, 설명이 필요한 작업은 상세 파일을 하나 만들면 됩니다. 자세한 방법은 일지 문서 상단의 작성 가이드에 있습니다.

## 문서를 추가할 때

`docs/` 아래에 새 문서를 만들면 [docs/README.md](README.md)의 목차에도 한 줄 추가해주세요. 목차에 없는 문서는 금방 잊힙니다.

아직 정리되지 않은 개인 초안은 `docs/draft/` 아래에 두시면 됩니다.
