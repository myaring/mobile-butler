# PR 룰

풀 리퀘스트의 말머리 등 양식 규칙입니다.

브랜치 전략과 커밋 메시지 양식은 [기여 양식 및 규칙](contribute_rules.md)에 있습니다. 이 문서는 **PR을 올린 다음부터 머지될 때까지**를 다룹니다.

양식이 조금 안 맞아도 머지는 됩니다. 아래 내용은 리뷰하는 사람이 PR을 열었을 때 "이게 뭘 바꾼 건지" 바로 알 수 있게 하려는 목적입니다.

---

## 한눈에 보기

| 항목 | 내용 |
| --- | --- |
| 보내는 곳 | **`dev` 브랜치** (`master`로 보내지 않습니다) |
| 올릴 수 있는 사람 | 참여자 전원 |
| 승인·머지 | **프로젝트 오너 1명** |
| 확인 시점 | **수요일 · 토요일 방송** (그 전까지 올라온 PR 대상) |

---

## 제목 말머리

```
<종류>: <무엇을 했는지 한 줄>
```

커밋 메시지와 같은 종류를 씁니다.

```
feat: 목표 입력 화면 추가
fix: 알림이 제조사 배터리 최적화로 누락되는 문제 수정
docs: PR 룰 및 기여 규칙 작성
chore: Room 종속성 추가
```

| 종류 | 쓰는 경우 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 작성·수정 |
| `refactor` | 동작은 그대로, 구조만 정리 |
| `test` | 테스트 코드 |
| `chore` | 빌드 설정, 종속성, 그 외 잡일 |

### 아직 작업 중이라면

의견을 먼저 듣고 싶거나 아직 완성되지 않은 PR은 **GitHub의 Draft PR**로 올려주세요. Draft를 쓰기 어려우면 제목 앞에 `[WIP]`를 붙여주셔도 됩니다.

```
[WIP] feat: 페이싱 엔진 계산 로직
```

Draft/WIP 상태의 PR은 리뷰 대상에서 빼고, 질문에만 답을 드립니다. 준비가 되면 Draft를 해제하거나 `[WIP]`를 지워주세요.

## 본문 양식

PR을 열면 템플릿이 자동으로 채워집니다. 해당하지 않는 항목은 지우고 올려주시면 됩니다.

- **작업 내용** — 무엇을 바꿨는지. 목록 몇 줄로 충분합니다
- **관련 이슈** — `#12` 처럼 번호를 적어주세요. `closes #12`로 적으면 머지와 함께 이슈가 닫힙니다
- **확인 방법** — 리뷰하는 사람이 어떻게 눌러보면 되는지. UI 변경은 **스크린샷이나 화면 녹화 한 장**이 설명 열 줄보다 빠릅니다
- **논의하고 싶은 점** — 자신 없는 부분, 다른 방법이 있을 것 같은 부분. 비워두셔도 됩니다

> 마지막 항목을 적어주시면 리뷰가 훨씬 빨라집니다. "여기 이렇게 했는데 맞는지 모르겠습니다"라고 적어주시면 그 부분을 먼저 봅니다.

## PR 크기

**가능하면 하나의 PR에 하나의 주제만 담아주세요.**

PR이 커지면 리뷰가 늦어지고, 문제가 생겼을 때 어디서 비롯된 것인지 찾기 어렵습니다. 기능 하나가 너무 크다면 쪼개서 여러 번 보내주셔도 됩니다. PR 개수가 많은 것은 전혀 문제가 되지 않습니다.

다만 이건 **권장이지 제한이 아닙니다.** 쪼개기 애매한 작업은 그대로 올리고 본문에 "이 부분까지 같이 들어갔습니다"라고 적어주세요.

### 섞이지 않게 해주시면 좋은 조합

- 기능 추가 + 관계없는 코드 전체 포맷팅
- 문서 수정 + 빌드 설정 변경
- 여러 사람이 동시에 건드리는 파일(`gradle/libs.versions.toml` 등)의 대량 수정

> 특히 종속성 파일은 충돌이 잦습니다. 이 파일만 바꾸는 작업은 짧게 끊어서 빨리 머지되게 하는 편이 모두에게 편합니다.
> [개발 일지](dev-log/README.md)는 표에 한 줄 추가 + 상세 파일 분리 구조라 충돌이 거의 없습니다. PR에 같이 담아주세요.

## 리뷰와 머지

### 확인 주기

PR은 **수요일과 토요일 방송에서 확인합니다.** 그 전까지 올라온 PR이 대상입니다.
금요일은 휴방이라 GitHub·Discord로만 소통합니다.

> 바로 머지되지 않아도 방치된 것이 아닙니다. 급한 PR이면 Discord에 알려주세요.

### 리뷰 의견이 달렸을 때

- 수정이 필요하면 **같은 브랜치에 커밋을 추가해서 push**하면 PR에 자동 반영됩니다. PR을 새로 만들 필요가 없습니다
- 의견에 동의하지 않으면 그렇게 답해주세요. 토론해서 정하면 됩니다. 리뷰 의견이 항상 맞는 것은 아닙니다
- 무슨 말인지 모르겠으면 그냥 모르겠다고 물어봐주세요. 그게 가장 빠릅니다

### 머지

- 머지는 **프로젝트 오너만** 수행합니다
- 다른 참여자의 PR에 승인(Approve)을 누르지 않아도 됩니다. 의견은 일반 코멘트로 남겨주세요
- 머지 후 작업 브랜치는 삭제해도 됩니다. GitHub에서 PR 머지 직후 나오는 `Delete branch` 버튼을 눌러주시면 됩니다

### 머지되지 않는 경우

가끔 PR이 머지되지 않고 닫힐 수 있습니다. 보통 아래와 같은 경우이고, 코드나 사람에 대한 평가가 아닙니다.

- 시즌 1 범위에 들어가지 않는 기능 ([일정과 범위](draft/hss900606_draft.md) 참고)
- 다른 PR과 내용이 겹친 경우
- 방향을 다시 의논해야 하는 경우

이유는 PR 코멘트에 남겨드립니다. 아깝다고 생각되는 부분이 있으면 Discord에서 다시 꺼내주세요.

## 자주 나오는 상황

**Q. `master`로 PR을 보내버렸습니다.**
PR을 닫지 않아도 됩니다. GitHub PR 화면에서 대상 브랜치(base)를 `dev`로 바꿀 수 있습니다. `Edit` 버튼 옆의 base 드롭다운에서 변경해주세요.

**Q. 충돌(conflict)이 났다고 나옵니다.**
[기여 규칙의 `dev` 최신화](contribute_rules.md#작업-시작-전-dev-최신화) 순서대로 최신 `dev`를 받아 병합한 뒤 push하면 해결됩니다. 어려우면 Discord에 올려주세요. 오너가 처리해도 됩니다.

**Q. 실수로 `local.properties` 같은 개인 파일을 커밋했습니다.**
PR 본문에 적어주시고, 해당 파일만 되돌린 커밋을 추가로 push해주시면 됩니다. 커밋 히스토리를 직접 고치려다 더 복잡해지는 경우가 많으니 먼저 물어봐주세요.

**Q. 이미 다른 사람이 같은 걸 만들고 있었습니다.**
둘 중 하나를 버리기보다, 어느 쪽을 기준으로 할지 Discord에서 정하고 나머지를 거기에 합치는 편이 보통 빠릅니다. 작업 시작 전에 이슈에 "제가 하겠습니다"를 남겨두면 이 상황을 대부분 막을 수 있습니다.
