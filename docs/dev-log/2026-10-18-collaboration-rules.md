## 한 일

여러 명이 기여하는 구조가 됐는데 브랜치·PR 규칙이 문서로 없어서, 비어 있던 규칙 문서 두 개를 채우고 PR 템플릿을 추가했습니다.

- [기여 양식 및 규칙](../contribute_rules.md) — 오너/참여자 역할, `master`·`dev` 2단 브랜치 전략, 브랜치·커밋 이름 규칙, 작업 시작 전 이슈 확인, 커밋 금지 파일
- [PR 룰](../PR_rules.md) — PR 대상은 `dev`, 제목 말머리, 본문 4항목, 리뷰·머지 절차, 자주 막히는 상황 Q&A
- `.github/pull_request_template.md` — PR 작성 창에 자동으로 채워지는 양식. 대상 브랜치와 개인 환경 파일 포함 여부를 체크리스트로 확인
- 루트 [README](../../README.md)에 "참여하기" 섹션 추가
- 개발 일지를 단일 표에서 **표 + 상세 파일** 구조로 개편하고 [템플릿](../templates/dev-log-template.md) 추가

## 알게 된 것 / 막힌 것

**개발 일지를 단일 파일 표로 유지하면 PR마다 충돌이 납니다.** 모두가 같은 표의 끝줄을 건드리기 때문입니다. 숙련자는 바로 해결하지만 초보자에게는 작업을 멈추게 하는 장애물이라, 상세 기록을 파일로 분리해 충돌 지점을 줄였습니다. 표에 남은 한 줄짜리 충돌은 해결법을 일지 상단에 적어뒀습니다.

형식은 기존 레포에서 쓰던 `docs/dev-log/YYYY-MM-DD-주제.md` 방식을 가져왔습니다. 다만 그쪽 템플릿의 검증 표와 메타데이터는 **빼기로 했습니다.** 혼자 쓰는 고강도 기록 양식을 초보자가 섞인 프로젝트에 그대로 적용하면 일지를 아예 안 쓰게 될 가능성이 더 큽니다. `2026/10/` 같은 연·월 중첩 디렉터리도 4주 프로젝트에는 과해서 평면 구조로 뒀습니다.

규칙 문서의 톤은 **필수가 아니라 권장**으로 통일했습니다. 양식 때문에 기여를 포기하는 쪽이 양식이 조금 어긋난 PR보다 손해라고 판단했습니다.
